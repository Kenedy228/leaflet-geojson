# Локальный PostGIS и геоданные

## Контур и конфигурация

`compose.yaml` фиксирует PostGIS 17 / 3.5 по digest. Сервис `db` публикует порт
только на `127.0.0.1` и хранит БД в именованном volume `pgdata`. Healthcheck
ожидает готовность PostgreSQL до запуска приложения. Проверено на Linux x86_64.
Нужны Docker Engine/Desktop и Docker Compose с `up --wait` (2.20+).

Из корня:

```sh
make init-env
make dev
```

Первая команда создаёт `.env` с новым случайным паролем и правами 0600,
не перезаписывая существующий файл. Вторая поднимает БД, дожидается healthcheck
и запускает Spring Boot с профилем `demo`: Flyway применяет схему и demo seed.
UI и API доступны на `http://localhost:8080`. После изменения JS перезапусти приложение.

`infra/manage.py` читает `.env` как данные, а не исполняет shell. Допустимы
`KEY=VALUE`, пустые строки, комментарии и значения в одинарных/двойных кавычках.
Значения с пробелами или `#` заключай в кавычки; `$` не интерполируется.
Переменные окружения имеют приоритет. `export`, подстановки и многострочные значения
не поддерживаются. Не применяй `. ./.env`: это другой, исполняемый shell-формат.

| Переменная | По умолчанию / действие |
| --- | --- |
| `DB_HOST` | `127.0.0.1`, для обычного `make run` |
| `DB_PORT` | `5432`, опубликованный порт локальной БД |
| `DB_NAME`, `DB_USER` | `gis`, имя БД и пользователя контейнера |
| `DB_PASSWORD` | Генерируется `make init-env`; в репозиторий не попадает |
| `SERVER_PORT` | `8080`, порт приложения |
| `CORS_ALLOWED_ORIGINS` | Пусто: same-origin; иначе список точных HTTP(S) origins через запятую |
| `EDITING_ENABLED` | `false`, серверный запрет записи, включая demo |
| `EDITOR_USERNAME`, `EDITOR_PASSWORD` | `make init-editor` настраивает локального редактора в приватном `.env` |
| `DB_URL` | Необязательный полный JDBC URL для `make run` |
| `COMPOSE_PROJECT_NAME` | `leaflet-geojson`; меняй для независимого локального контура |
| `MAVEN_ARGS` | Дополнительные Maven-флаги, например отдельный dependency cache |

`make dev` всегда подключается к локальному Compose через `DB_PORT`/`DB_NAME`,
не использует внешний `DB_URL`. `make run` не запускает БД и не включает demo:
он подходит для подготовленной внешней БД и реального OSM-импорта.
Для внешней БД нужны права создания схем/объектов и установки расширений,
если они ещё отсутствуют. Локальный контейнер использует пользователя-владельца
для миграций; разделение эксплуатационных ролей здесь не реализовано.

`Ctrl+C` останавливает приложение. `make db-down` останавливает только локальную БД
и сохраняет volume; `make db-up` поднимает её снова. Изменение `DB_PASSWORD` в `.env`
не меняет пароль внутри уже созданного volume: меняй роль PostgreSQL отдельно
или восстанавливай подготовленную резервную копию в согласованное окружение.

## CORS

Обычный запуск обслуживает UI и `/api/v1/osm` из Spring Boot на одном origin.
Отдельный Live Server не требуется: относительный API URL следует адресу страницы,
включая изменённый `SERVER_PORT`. По умолчанию сервер не выдаёт CORS-разрешения.

Если отдельному клиенту нужен доступ к API из браузера, задай в `.env`, например:

```dotenv
CORS_ALLOWED_ORIGINS=http://localhost:5173,https://viewer.example.test
```

Перезапусти приложение. Origin состоит из схемы, хоста и необязательного порта;
`localhost` и `127.0.0.1`, разные схемы и порты — разные origins. Пробелы вокруг
элементов допустимы; пустое значение отключает разрешения. Wildcard, `null`, пути,
завершающий `/`, query, fragment и реквизиты запрещены: ошибочная настройка
прерывает запуск, а её значение не выводится в сообщении валидации.

Разрешения действуют только на `/api/v1/osm/**`: GET, POST и DELETE, заголовок
`Content-Type`, включая preflight. Credentials/cookies не разрешены. Статические
файлы не получают CORS-разрешений. Конфигурация через
[Spring MVC](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc-cors.html).
Отдельный клиент должен обращаться к адресу API или использовать свой proxy:
эта настройка не меняет относительный URL существующего frontend.

CORS управляет браузерным доступом к ответам и не заменяет авторизацию/CSRF-защиту.
Изменение общих точек защищено сессией редактора и CSRF, по умолчанию отключено.
Редактирование same-origin: credentials и CSRF-заголовок в CORS не добавлены.
Держи учебный контур локальным. [Настройка и HTTP-контракт](../docs/access-control.md).
Публично показанный ранее пароль относился только к одноразовой demo-БД
(подтверждено автором для #3). Для нового контура используется новый сгенерированный
пароль; не повторяй прежние значения. Ротация роли в существующем volume выполняется
отдельно от редактирования `.env`.

## Схема и сохранность данных

История Flyway остаётся в `app.flyway_schema_history`:

- V1/V2 создают пользовательскую модель и явный legacy-перенос; они не изменены.
- V3 создаёт совместимые `public.planet_osm_point`, `planet_osm_roads`,
  `planet_osm_polygon`, hstore и пространственные индексы.
- Существующие таблицы не заменяются. Добавляется недостающий `tags` hstore;
  неподходящие SRID/тип `tags` приводят к отказу миграции вместо скрытой конвертации.
- `way` хранится в EPSG:3857, пользовательские `app.user_points.geom` — в EPSG:4326.
  Reference ID не UNIQUE: OSM может иметь несколько геометрий, а legacy-строки — коллизии.

Таблицы приложения и UUID не зависят от импорта в `public`.
Не удаляй volume или схему `app` для обновления OSM. Старые пользовательские точки
переносятся только по [явно проверенным ID](../docs/user-points.md).

## Demo-набор и лицензия

В `backend/src/main/resources/db/demo/R__reference_dataset.sql` находится
фиксированный небольшой фрагмент Железногорска: 3 точки, 2 дороги и 2 полигона
около исходного центра карты. Данные получены **одним запросом** официального OSM API
2026-11-01 для bbox `35.34,52.33,35.36,52.35`. SQL содержит URL, SHA-256 исходного
ответа, OSM ID, версии и timestamps выбранных объектов. Геометрии и использованные
теги сохранены; usernames, UID редакторов и changeset metadata не включены.
Новый запуск не скачивает геоданные из сети.

Данные © OpenStreetMap contributors, распространяются на условиях
[Open Database License 1.0](https://opendatacommons.org/licenses/odbl/1-0/).
[Источник и атрибуция](https://www.openstreetmap.org/copyright).
Код приложения распространяется по [MIT](../LICENSE); OSM-данные сохраняют условия
ODbL. На карте показана ссылка на OpenStreetMap contributors; OSM-тайлы остаются
внешним сервисом.

Demo активируется только профилем `demo` либо явной командой:

```sh
make db-seed
make db-reset-demo
```

Обе команды атомарно восстанавливают этот demo-снимок, не накапливая дубликаты.
Строки отмечены служебным hstore-тегом `leaflet:demo`; пользовательские точки
не удаляются. Если reference-таблицы содержат чужие/реально импортированные строки,
операция отказывается от изменения и оставляет данные на месте. Не смешивай demo
и полный импорт в одной БД. Команды seed/reset предполагают уже применённые миграции.

Repeatable seed всегда присутствует среди доступных миграций, но обычный профиль
задаёт `demo_data_enabled=false`, и SQL ничего не меняет. В demo-профиле значение
`true`; изменение placeholder меняет checksum и повторно применяет seed.
Поэтому переключение профилей на одном volume не создаёт missing-migration ошибки.
Сырой SQL содержит Flyway-placeholder: используй команды выше, а не прямой запуск файла.

## Резервная копия и восстановление

Сначала создай копию локальной БД:

```sh
make db-backup
# либо свой новый файл:
make db-backup BACKUP_FILE=backups/before-import.dump
```

Файл custom-format создаётся с правами 0600, не перезаписывает существующий,
содержит reference-таблицы, пользовательские точки и Flyway history.
Пароли ролей в эту копию не входят. `backups/` и `*.dump` игнорируются Git.
При ошибке выгрузки неполный файл удаляется.

Для восстановления **останови backend**, проверь правильность файла и целевого
локального Compose-контура, затем:

```sh
make db-up
make db-restore BACKUP_FILE=backups/before-import.dump CONFIRM_RESTORE=YES
make run
```

Восстановление заменяет содержимое локальной БД, включая пользовательские записи,
состоянием копии. Без пути и явного подтверждения оно не запускается.
`pg_restore` работает в одной транзакции; используй доверенную копию совместимой
версии приложения. Эта команда не предназначена для внешней БД из `DB_URL`.

## Необязательный полный OSM-импорт

Большой PBF не нужен для запуска курсового. Для отдельной БД с реальным импортом:

1. Возьми небольшой региональный `.osm.pbf` у [Geofabrik](https://download.geofabrik.de/)
   либо другого провайдера OSM. Зафиксируй URL, дату, SHA-256 и ODbL-атрибуцию.
2. Подними БД, один раз запусти `make run` для миграций, останови приложение,
   сделай backup. Не включай профиль demo в этой БД.
3. Используй osm2pgsql 2.x с поддержкой существующего **legacy pgsql output**.
   Параметры совместимого профиля приведены ниже; проверь установленную версию
   и `--help`. Pgsql output помечен upstream как deprecated; Flex output без
   собственного совместимого style не создаёт нужный контракт таблиц автоматически.
4. Создай отдельную схему `osm_import` для middle-таблиц. Затем выполни импорт
   с учётными данными этой отдельной БД; пароль передавай через `PGPASSWORD`/pgpass,
   не через аргументы командной строки:

```sh
osm2pgsql --create --slim --output=pgsql --merc --hstore-all \
  --prefix=planet_osm --output-pgsql-schema=public --middle-schema=osm_import \
  --host=127.0.0.1 --port=5432 --database=gis --username=gis region.osm.pbf
```

Используется default.style установленной версии. `--merc` сохраняет EPSG:3857,
`--hstore-all` обеспечивает `tags` (включая leisure/landuse); имена и highway —
обычные колонки. `planet_osm_roads` — подмножество для low-zoom rendering,
а не все highway-объекты. `--create` заменяет импортированные таблицы: backend
должен быть остановлен. Не указывай схему `app` как output/middle и не сбрасывай
всю БД. После импорта запусти **`make run`**, проверь три слоя, источник геометрий,
имена и сохранность пользовательских UUID.

[Официальное руководство osm2pgsql](https://osm2pgsql.org/doc/manual.html)
описывает профиль и требования к правам/схемам. Большой внешний PBF в рамках
проверки этого изменения не загружался; SQL-контракт, SRID и сохранность app-данных
проверяются отдельно на небольшом наборе.

## Тестовый контур

`make test` / `make verify` автоматически поднимают `test-db` в новом уникальном
Compose project на случайном localhost-порту. У него tmpfs вместо dev-volume;
миграции создают схему с нуля. После тестов удаляются только этот project и его
ресурсы, в том числе при обычной ошибке теста. Рабочая `.env`/`DB_URL` не выбирают
тестовую БД. Frontend и CLI unit-тесты не требуют Docker.

При явной необходимости можно передать `TEST_DB_URL`, `TEST_DB_USER`,
`TEST_DB_PASSWORD`: тогда используется указанная **отдельная тестовая БД**, и
создание/удаление контейнера отключено. Эти тесты меняют данные; не указывай личную
или demo-БД. Автоматический вариант предпочтителен.

Проверено 2026-11-01 на отдельном локальном Compose project из чистой копии:

- `make verify`: 16 backend-, 2 frontend- и 3 CLI-теста; сборка JAR успешна.
- Новый пустой volume: `make init-env` → `make dev` создаёт БД, схему и 7 demo-объектов.
- Повторный seed/reset не дублирует строки и сохраняет пользовательский UUID/геометрию.
- Backup не перезаписывает файл; restore без подтверждения отклоняется, с подтверждением
  восстанавливает удалённую пользовательскую точку и историю миграций.
- Переходы `demo → normal → demo` на одном volume проходят без missing migration;
  удаление/пересоздание контейнера с тем же named volume сохраняет данные.
- `make verify` при работающем demo использует другой контейнер и не меняет его данные.
- Реальное обновление предыдущего JAR (V1/V2) до V3 сохранило OSM EWKB/имена/ID,
  оба legacy-объекта с совпавшим ID, пользовательский UUID и checksums V1/V2.
- Chromium: три слоя, дистанция, создание/удаление точки; атрибуция видна и доступна
  с клавиатуры при 1536px и 390px. Scoped axe для attribution не выявил нарушений;
  это не аудит доступности всей legacy-страницы.
- Mutation-проверки подтвердили, что тесты ловят накопление дублей, отсутствие
  защиты чужого импорта, отключающего gate и ошибочную проекцию seed.
