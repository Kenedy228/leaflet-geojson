# Ограниченные геовыборки и дистанция

## HTTP-контракт

`GET /api/v1/osm/points`, `/roads`, `/polygons` возвращают прежние массивы DTO.
Новые необязательные query parameters:

- `bbox=west,south,east,north` — четыре конечных десятичных WGS84-числа;
  долготы в [-180,180], широты в [-90,90], south<north. west>east означает
  пересечение антимеридиана. Нулевая ширина, включая 180→−180, недопустима.
- `zoom` — целое 0..22, определяет только детализацию отображения линий/полигонов.

Повторение параметра, пустой или неверный формат даёт 400 `invalid_spatial_query`.
Без bbox используется весь мир; без zoom —22. Это совместимость прежних клиентов,
а не безлимитный экспорт: все ограничения действуют и для запросов без параметров.
Встроенный frontend всегда передаёт область и zoom своей карты.
Полный контракт и статусы находятся в [openapi.json](openapi.json).

## Лимиты и ошибки

| Ограничение | Поведение |
| --- | --- |
| 500 исходных подходящих объектов на слой | При 501 возвращается 413 `spatial_limit_exceeded`; успешный ответ не обрезается |
| 5000 вершин на объект, 20000 суммарно на слой после обработки | При превышении 413 `spatial_geometry_limit_exceeded` до GeoJSON |
| 2 с на spatial SQL, включая distance | JDBC statement timeout →503 `spatial_query_timeout` с безопасным сообщением |
| 2..1000 точек distance | Невалидный пакет 400; один параметризованный SQL на все соседние пары |

При 413 нужно приблизить карту или сузить область. Frontend показывает серверную
причину, сохраняет checked-состояние и позволяет повторить загрузку; движение
карты запрашивает новую область. Частичная выдача никогда не выглядит полной.
Счётчик ограничивает исходные пересекающиеся объекты консервативно: некоторые
могут дать только границу нулевой размерности при clipping и не попасть в ответ.

## SQL и детализация

Реальные запросы строит `SpatialService`; benchmark использует тот же SQL и
параметры, а не похожую тестовую копию.

1. WGS84 bbox преобразуется в CRS хранимой геометрии, а не каждый объект в WHERE.
   Для OSM3857 широта bbox обрезается до ±85.0511287798066; запрос целиком за этим
   диапазоном не возвращает OSM. Пользовательские точки 4326 сохраняют допустимые
   полюса. Wrapped bbox проверяется через два отдельных indexable диапазона с OR,
   чтобы не сканировать bounding box почти всего мира и не дублировать объекты.
2. `&&`/`ST_Intersects` применяются к исходному индексированному столбцу. Используются
   существующие GiST `planet_osm_*_way_idx` и `user_points_geom_idx`.
   Сохраняются предметные фильтры: именованные OSM-точки/полигоны и дороги с highway.
3. Materialized candidates ограничены 501. При переполнении clipping/сериализация
   не выполняются. OSM и пользовательские точки делят один общий лимит 500.
4. Линии/полигоны обрезаются по bbox в 3857, извлекается нужная размерность,
   применяется `ST_SimplifyPreserveTopology`. Допуск равен
   `max(0.05,156543.03392804097 / 2^zoom)` **метров Web Mercator** — примерно одному экранному
   пикселю с минимальным допуском0.05м; это не обещание геодезической точности. Пустые и boundary-only результаты
   меньшей размерности исключаются. У полностью покрытого объекта clipping
   пропускается; выходные вершины проверяются до `ST_Transform`/`ST_AsGeoJSON`.
5. Все данные сериализуются в WGS84 после пространственного отбора и проверок.
   Точки не упрощаются. Distance использует точные координаты и WGS84 geography,
   `LEAD` с явным порядком, затем сумму сегментов в исходном порядке.

[PostGIS описывает index-aware predicates](https://postgis.net/docs/using_postgis_query.html),
а [PostgreSQL17 EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html)
объясняет различия SeqScan/IndexScan и накладные расходы ANALYZE. Наличие индекса
не означает, что планировщик обязан выбирать его для любой области или маленькой
таблицы. План проверяется на селективном представительном наборе ниже.

## Viewport и состояние UI

Leaflet сообщает текущие bounds/zoom, изменение сразу обесценивает ожидаемые
ответы и очищает данные предыдущей области. Загрузка включённых слоёв объединяется
таймером 150 мс. Выключенный слой не восстанавливается поздним ответом; таймеры,
запросы и map listeners освобождаются при уничтожении.

Черновики и выбранные для дистанции координатные снимки сохраняются при pan/zoom.
Новые подтверждённые точки показываются только в текущем bbox; свежий успешный
GET остаётся авторитетным относительно более ранних overlays. Векторы размещаются
в видимой копии мира независимо от canonical долготы; связные части reference-геометрии
переносятся целиком, а не по отдельным вершинам. Координаты API при этом не меняются.
Скрытие points
по-прежнему сбрасывает маршрут. [Модель frontend](frontend.md).

## Воспроизводимые измерения

```sh
make benchmark-spatial
# Свой Maven cache при необходимости:
# make benchmark-spatial MAVEN_ARGS='-B -ntp -Dmaven.repo.local=/tmp/leaflet-m2'
```

Команда поднимает отдельный tmpfs PostGIS с production Flyway и случайным портом,
запускает `SpatialQueryBenchmark` и удаляет БД в finally. `TEST_DB_URL` для этой
команды запрещён; прямой вызов benchmark-класса без специальной отметки изоляции
завершится до INSERT. Личные БД, дампы и secrets не нужны.

Fixture синтетическая и детерминированная:50000 OSM-точек,1000 пользовательских,
10000 дорог и 5000 полигонов. Есть глобальная разреженная сетка, городской кластер
и отдельный overflow-кластер 600 точек. Городские дороги имеют 80 входных вершин;
полигоны строятся с 81 вершиной. Городской viewport
`35.3,52.3,35.4,52.4&zoom=13` содержит 380 точек,200 дорог,100 полигонов.
Исходный рецепт — в [SpatialQueryBenchmark](../backend/src/test/java/com/github/gis/geo/SpatialQueryBenchmark.java).

Отчёт — `backend/target/spatial-benchmark.json`: actual production SQL
`EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)`, индексы и реальные HTTP-ответы.
Первый SQL/HTTP замер записывается отдельно; затем 20 прогретых образцов,
p95 — nearest-rank. Данные после INSERT/ANALYZE уже в cache: это не cold-cache тест.
EXPLAIN включает profiling overhead; HTTP включает полный UTF-8 body.

Заранее выбранные локальные цели: SQL p95≤200 мс, HTTP p95≤500 мс,
ответ≤2 MiB для указанного viewport. Это бюджет учебного проекта на объявленном
наборе, не SLA произвольного сервера/дампа и не тест конкурентной нагрузки.
1000-точечный distance проверяется отдельно; один SQL round-trip подтверждён
реальной JDBC-инструментацией в BatchedDistanceTests.

Измерено 2026-11-01: Linux amd64,16 logicalCPU, JDK25.0.5, PostgreSQL17.5,
PostGIS3.5.2; образ фиксирован digest в compose. Все три локальных бюджета выполнены.

| Слой | Объектов | Первый SQL,мс | Первый HTTP,мс | SQL p95,мс | HTTP p95,мс | UTF-8 body,bytes |
| --- | --- | --- | --- | --- | --- | --- |
| points | 380 | 1.652 | 146.339 | 1.914 | 10.037 | 63960 |
| roads | 200 | 26.731 | 38.500 | 27.154 | 33.391 | 198181 |
| polygons | 100 | 7.282 | 11.824 | 7.729 | 11.416 | 37701 |

Distance1000 точек/999 сегментов: HTTP p95 15.573 мс.
В плане points используются `planet_osm_point_way_idx` и `user_points_geom_idx`,
roads — `planet_osm_roads_way_idx`, polygons — `planet_osm_polygon_way_idx`.
Overflow-кластер даёт 413 `spatial_limit_exceeded`, а не частичный массив.
[Полные 20 образцов, EXPLAIN ANALYZE/BUFFERS и версии](benchmarks/2026-11-01-spatial.json).

Benchmark запускается отдельно от обязательного CI: latency-пороги не делают
проверки зависимыми от скорости hosted runner. Функциональные 500/501, vertex limits,
invalid bbox/zoom, dateline/poles, cancellation и 1000 точек входят в обычный CI.
