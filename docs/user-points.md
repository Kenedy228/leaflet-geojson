# Пользовательские точки и идентификаторы

Реализация [#7](https://github.com/Kenedy228/leaflet-geojson/issues/7).

## Модель

OSM-слои находятся в `public.planet_osm_*`. API только читает импортированные
точки: изменение и удаление OSM-объектов через него запрещены.
Новые пользовательские точки хранятся в `app.user_points`:

| Поле | Назначение |
| --- | --- |
| `id` | UUID PK, генерируется PostgreSQL через `gen_random_uuid()` |
| `name` | Непустое название, до 255 символов |
| `geom` | Point в WGS84 / EPSG:4326, longitude/latitude |
| `legacy_osm_id` | Прежний ID только для перенесённых записей; не UNIQUE |
| `created_at` | Время создания записи |

Есть GiST-индекс геометрии. Ссылок FK на импортированные OSM-таблицы нет:
замена импорта в `public` не должна удалять или перенумеровывать пользовательские точки.
Нельзя сбрасывать всю БД, схему `app` или восстанавливать поверх неё старый полный дамп
при обычном обновлении OSM.

Точки пока **общие**, персонального владельца нет. Серверная авторизация записи
и удаления реализуется в [#4](https://github.com/Kenedy228/leaflet-geojson/issues/4).
Проверка источника объекта не заменяет проверку прав пользователя.

## Миграции

Flyway автоматически управляет только схемой `app`; его history —
`app.flyway_schema_history`. `V1` создаёт пользовательскую таблицу и индекс,
`V2` устанавливает функцию явного legacy-переноса. Наличие данных в `public`
не требует `baseline-on-migrate`: public не является схемой миграций Flyway.

Для первого запуска нужны права создания схемы `app` и её объектов.
PostGIS должен быть установлен в БД в `public`: `V1` выполняет
`CREATE EXTENSION IF NOT EXISTS postgis WITH SCHEMA public`, что требует
соответствующих прав, если расширение ещё отсутствует.
Миграции OSM, seed и Compose относятся к #2 и пока не добавлены.

## API точек

Endpoints остаются под `/api/v1/osm`. Формат идентификатора изменён:

- `osm:<osm_id>` — импортированная точка, только чтение.
- `user:<uuid>` — пользовательская точка.

Клиент должен считать `id` непрозрачной строкой и передавать её целиком.
Внешний `osm_id` тоже возвращается строкой: bigint может превышать точность
JavaScript Number. У пользовательских точек `osm_id` равен `null`.
`legacy_osm_id` — служебное происхождение записи, а не её текущий ID.

`GET /points` возвращает массив объектов:

```json
{
  "id": "user:0243590a-aef2-43e5-b3b5-752266d68589",
  "source": "user",
  "osm_id": null,
  "name": "Новая точка",
  "geojson": "{\"type\":\"Point\",\"coordinates\":[35.350871,52.339203]}"
}
```

`geojson` пока остаётся JSON-строкой для совместимости с существующим frontend.
В геометрии порядок координат `[lng, lat]`.

`POST /points/add` принимает 1–1000 объектов с именованными координатами:

```json
[{"name":"Новая точка","lat":52.339203,"lng":35.350871}]
```

Успех — HTTP 201, `{"inserted":1,"points":[...]}`. `points` содержит полные
объекты с серверными ID в порядке входного массива. Имена должны быть непустыми,
до 255 символов, координаты — конечными, lat в [-90,90], lng в [-180,180].
Валидация выполняется до записи; пакет записывается транзакционно.
HTTP 400 означает некорректный ввод; ошибка БД даёт 500 и откатывает весь пакет.
Повтор запроса после потери ответа ещё не имеет ключа идемпотентности.

`DELETE /points/{id}` принимает полный ID:

| Ответ | Значение |
| --- | --- |
| 204 | Удалена ровно выбранная пользовательская точка |
| 400 | ID без namespace или некорректный user UUID |
| 403 | Попытка удалить импортированный OSM-объект |
| 404 | Пользовательской точки с таким UUID нет |

Маршруты дорог, полигонов и расстояний не меняются. Общий формат ошибок и полный
OpenAPI ещё относятся к #8/#19.

## Перенос ранее добавленных точек

Старая версия записывала пользовательские точки в `planet_osm_point` с отрицательным
timestamp ID. У этих строк нет надёжной метки владельца/происхождения; одного знака
или диапазона ID недостаточно для автоматического переноса.

Перенос **не запускается при старте** и не имеет HTTP endpoint. Оператор:

1. Делает резервную копию и останавливает старые writers/импорт на время переноса.
2. Проверяет происхождение и **все строки** выбранных ID, включая совпадения ID.
   Функция переносит `name`, геометрию и прежний ID; прочие OSM-атрибуты не копируются.
3. Сначала проверяет перенос на копии БД. Для явно подтверждённых ID выполняет:

   ```sql
   BEGIN;
   SELECT app.migrate_legacy_user_points(ARRAY[-1735689600000]::bigint[]);
   -- Проверить новые записи, количество, имена и координаты.
   COMMIT; -- либо ROLLBACK, если результат не подтверждён
   ```

4. Сверяет число и координаты новых записей и сохраняет соответствие через
   `legacy_osm_id`. Клиенты после переноса заново загружают список точек.

Вызов разрешает только непустой список отрицательных ID. Каждая исходная строка,
даже с одинаковым `osm_id`, получает отдельный UUID; геометрия преобразуется в 4326.
Строки источника удаляются и вставляются в одной атомарной SQL-операции.
При ошибке имени, геометрии или ограничения удаление откатывается.
Повторный вызов для уже перемещённых строк возвращает 0; невыбранные ID остаются
на месте и отображаются как readonly OSM до явного решения оператора.

Не добавляй UNIQUE к `legacy_osm_id`: это потеряло бы строки старых коллизий.
Функция работает с правами вызывающего (`SECURITY INVOKER`) и не даёт ему
дополнительных прав на OSM. Импортировать следует OSM-данные без старых смешанных
пользовательских записей; восстановление старого смешанного дампа может вернуть
их в источник повторно и требует отдельной сверки.

## Frontend

Черновик имеет строковый ID `draft:<счётчик>`; BigInt-счётчик монотонен в пределах
страницы и не зависит от случайности или доступности secure context.
После подтверждённого POST временные маркеры заменяются объектами с серверными ID,
если слой точек включён. Скрытый слой загрузит их при следующем включении.
Отправленные поля блокируются до ответа; новые черновики остаются в очереди.
Удаление и выбор используют ID, а не совпадение имени и координат.

Это изменение не закрывает все гонки загрузки слоёв и расчётов из #12/#13,
не вводит авторизацию #4 и не исправляет все HTML popup из #5.

## Результаты проверки

Проверено на отдельном временном PostgreSQL 17 / PostGIS 3.5:

- `make verify`: 11 backend-тестов и 2 frontend-регрессии, без ошибок.
- 24 параллельных создания получили разные UUID; OSM-таблица не пополнилась.
- Две legacy-строки с совпавшим ID получили разные UUID; повторный перенос дал 0,
  невыбранная строка осталась, ошибочная вставка откатила удаление источника.
- Реальный JAR сохранил пользовательский UUID, имя и координаты после удаления,
  пересоздания и заполнения всех трёх OSM-таблиц в тестовом контейнере.
- Chromium проверил readonly OSM, получение серверных ID без перезагрузки,
  независимый выбор одинаковых по имени/координатам точек, сохранность нового
  черновика при задержанном POST и точечное удаление. Ошибок JavaScript не было.
- Независимое review не выявило замечаний в рамках #7.

Личная БД автора не использовалась; её legacy-данные автоматически не переносились.
