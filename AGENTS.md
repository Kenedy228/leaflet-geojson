# Инструкции для агентов

## Назначение и область действия

Учебное GIS-приложение для курсовой работы 4 курса и GitHub-портфолио.
Основные сценарии: просмотр точек, дорог и полигонов, создание и удаление
пользовательских точек, расчёт геодезического расстояния между выбранными точками.
Результат должен воспроизводимо запускаться локально и проверяться автоматически.
Публичное развёртывание не входит в текущую задачу.

Этот файл действует на весь репозиторий. Перед изменением файлов прочитай
применимые вложенные `AGENTS.md`: они уточняют правила для своих каталогов.
Явные инструкции пользователя имеют приоритет над правилами репозитория.

## Текущее состояние и целевая структура

Сейчас приложения объединены в одном checkout:

- `frontend/` — статические HTML/CSS/JavaScript-файлы и карта Leaflet.
  `index.html`, `index.css`, `index.js` содержат страницу и инициализацию;
  `points.js`, `roads.js`, `polygons.js` — геослои;
  `add-point.js`, `delete-point.js`, `distance.js` — операции с точками;
  `constraints.js` — относительный путь API.
- `backend/` — Maven-проект Java 25 / Spring Boot 3.5.7 с JdbcTemplate и PostGIS.
  Maven включает frontend в static resources; UI и `/api/v1/osm` доступны с одного сервера.
- `docs/` — происхождение исходников и документация; см. [migration.md](docs/migration.md).
- `Makefile`, `.env.example` — корневые команды и пример конфигурации окружения.

Backend импортирован снимком из https://github.com/Kenedy228/leaflet-geojson-backend.
Проверяй актуальный `backend/pom.xml` перед работой; наличие зависимостей JPA
не означает, что запросы реализованы через ORM.

Согласованная дальнейшая цель: Svelte 5 + TypeScript в строгом режиме + Vite
в `frontend/`, воспроизводимое локальное окружение в `infra/`, архитектура,
модель данных и OpenAPI в `docs/`. Flyway уже управляет пользовательскими точками
в схеме `app`; Svelte, `infra/`, миграции OSM и CI ещё не созданы.
Не выдавай планируемое устройство за реализованное. Сохраняй выбранный стек;
его замена требует согласования с пользователем.
Реализуй целевую структуру постепенно в рамках соответствующих issues.
Не создавай пустые каталоги, конфигурации, миграции или дополнительные инструменты,
если они не нужны для текущей задачи.

Источники требований:

- [Roadmap и порядок работ](https://github.com/Kenedy228/leaflet-geojson/issues/20).
- [Объединение репозиториев](https://github.com/Kenedy228/leaflet-geojson/issues/1).
- [Переход на Svelte](https://github.com/Kenedy228/leaflet-geojson/issues/21).
- [Архитектура и OpenAPI](https://github.com/Kenedy228/leaflet-geojson/issues/19).
- [README](https://github.com/Kenedy228/leaflet-geojson/issues/22).

Критерии конкретного issue определяют объём изменения. Связанные задачи закрывай
только после проверки их собственных критериев.
Проблемы вне области текущего issue фиксируй отдельно и сообщай пользователю.
Исправляй их в текущей задаче только тогда, когда они блокируют её выполнение
или проверку; иначе оставляй для отдельного изменения.

## Доступные команды

Все команды этого раздела выполняются из корня репозитория.
Нужны полный JDK 25, GNU Make и POSIX shell; Node.js 22 — для frontend-проверок.
Maven 3.9.11 загружается wrapper-скриптом при первом запуске.

Для запуска и интеграционных тестов нужна отдельная подготовленная PostGIS БД
с OSM-таблицами и hstore. Flyway автоматически создаёт `app` и её историю;
полное окружение и миграции OSM пока не добавлены. Для тестов используй отдельную
БД с `backend/src/test/resources/fixtures/osm.sql`, не личную/demo-БД.
Настрой `.env` по `.env.example` и экспортируй локальные переменные:

```sh
set -a
. ./.env
set +a
make run
```

`.env` автоматически не загружается. Команда `. ./.env` исполняет shell-содержимое,
поэтому используй только свой локальный файл. Открывай `http://localhost:8080`
(либо порт `SERVER_PORT`). Не запускай frontend через обычный статический сервер:
относительный `/api/v1/osm` должен обслуживаться тем же Spring Boot приложением.
После изменения frontend перезапускай `make run` для обновления Maven-ресурсов.

```sh
make check    # Синтаксис frontend/*.js и git diff --check
make build    # JAR без запуска тестов
make test-frontend  # Регрессии идентификаторов черновиков, без БД
make test     # Frontend и backend; нужны реквизиты отдельной подготовленной тестовой БД
make verify   # Проверки, тесты и упаковка JAR
```

Без Make запускай из `backend/` команды `./mvnw spring-boot:run`,
`./mvnw -DskipTests package`, `./mvnw test` или `./mvnw verify`;
в Windows используй `mvnw.cmd`. Собранное приложение запускается из корня:

```sh
java -jar backend/target/gis-0.0.1-SNAPSHOT.jar
```

У frontend пока нет `package.json`, отдельной сборки, lint или проверки TypeScript.
Регрессии в `frontend/tests/` запускаются через Node test runner без npm-зависимостей.
Проверка синтаксиса не заменяет эти тесты и проверку UI в браузере.
Обновляй команды, рабочие каталоги, версии и условия запуска в том же изменении,
которое добавляет Svelte, миграции или CI. Не выдумывай отсутствующие команды.
Подробности настройки и ограничения описаны в [README.md](README.md).

## Правила реализации

- Используй явную модель состояния: сохранённые объекты, черновики, выбор точек
  и состояние запросов должны быть согласованы. Не переноси глобальное изменяемое
  состояние и ручную синхронизацию DOM из текущего JavaScript в Svelte.
  Используй реактивное состояние Svelte 5; экземплярами Leaflet и другими внешними
  объектами управляй с учётом жизненного цикла компонентов. Конфигурационные
  константы на уровне модуля допустимы.
- Сохрани существующие пользовательские сценарии при переносе на Svelte.
  Выделяй компоненты по ответственности; API-клиент и типы держи отдельно от UI.
- Создавай Leaflet-карту после появления DOM-контейнера. При уничтожении компонента
  освобождай карту, обработчики и запросы. Не допускай повторных подписок.
- Обрабатывай сетевые ошибки и неуспешные HTTP-статусы. Отменяй или игнорируй
  устаревшие ответы. Сохранение работает со снимком отправленных черновиков и
  не удаляет более поздние изменения; повторная отправка должна контролироваться.
- Пользовательские названия выводи как текст. Строки `bindPopup` интерпретируются
  как HTML: используй безопасный DOM с `textContent`. Не вставляй пользовательские
  значения через `innerHTML` или `{@html}`.
- Проверяй права на изменения на сервере. Скрытая кнопка и CORS не заменяют
  авторизацию. Не помещай секрет администратора в frontend.
- До реализации авторизации зафиксируй модель владения точками: общие с доступом
  по ролям либо персональные. Для персональных точек сервер проверяет принадлежность
  объекта при изменении и удалении; не доверяй идентификатору владельца из запроса.
  Полноценная система регистрации и внешняя IAM не требуются без отдельной задачи.
- Изменения API согласовывай с клиентом и OpenAPI. Валидируй входные данные,
  определяй ошибки HTTP и не возвращай успешное сохранение при отказе записи.
  SQL выполняй с параметрами; внутренние ошибки и секреты не должны попадать в ответ.
- Соблюдай доступность: уникальные ID, связанные подписи, управление клавиатурой,
  доступные имена кнопок и видимые состояния ошибок. Не скрывай атрибуцию OSM.

## Геоданные и БД

- В GeoJSON и текущем запросе distance координаты идут как `[lng, lat]`.
  Leaflet обычно принимает `[lat, lng]`; преобразование делай явно на границе.
  Текущий запрос создания точки использует именованные поля `lat` и `lng`.
- Внешние координаты — WGS84 / EPSG:4326. Существующий backend преобразует
  импортированную геометрию в EPSG:4326 при чтении; старые пользовательские точки
  записывались в OSM-таблицу в EPSG:3857.
  Новые пользовательские точки хранятся в `app.user_points` в EPSG:4326.
  Фактическую схему импортированной БД нужно проверить; миграции OSM должны закрепить SRID.
- Расстояния между последовательно выбранными точками рассчитывай в метрах
  на сфероиде WGS84 через PostGIS `geography` или эквивалентный геодезический метод.
  Общая дистанция — сумма этих сегментов; это не длина маршрута по дорогам.
  Геометрии EPSG:3857 перед приведением к `geography` преобразуй в EPSG:4326
  через `ST_Transform`, а не просто меняй метку SRID. Не заменяй геодезический
  расчёт евклидовым расстоянием по градусам или координатам Web Mercator.
- Валидируй порядок, конечность и диапазоны координат, учитывая ограничения
  выбранной проекции; ограничивай размер пакетов и геовыборок.
- Пользовательские точки общие, хранятся отдельно от OSM и получают UUID от БД.
  API использует строковые ID `osm:<osm_id>` и `user:<uuid>`; не преобразуй их
  или внешний `osm_id` в JavaScript Number. OSM-точки доступны только для чтения.
  Подробный контракт и явный legacy-перенос — в [user-points.md](docs/user-points.md).
  Не считай отрицательный ID достаточной меткой происхождения; не запускай
  legacy-перенос автоматически. Не сбрасывай `app` при повторном импорте `public`.
  Не считай timestamp или случайное число из небольшого диапазона уникальным ID.
- Изменения схемы оформляй версионированными миграциями. Не редактируй применённые
  миграции ради нового изменения. Seed должен быть небольшим и воспроизводимым.
- Не используй личную БД автора для тестов. Импорт и повторный seed не должны
  уничтожать пользовательские данные. Разрушительные операции с данными требуют
  соответствующего разрешения пользователя.

## Проверки и завершение работы

- До изменения проверь `git status` и существующий diff. Не перезаписывай чужие
  изменения; не выполняй разрушительные Git-операции без разрешения пользователя.
- Не коммить секреты, локальные `.env`, дампы с личными данными и логи с реквизитами.
  Примеры конфигурации должны содержать безопасные заглушки.
- Исправления поведения сопровождай проверкой исходного ошибочного сценария.
  Для UI проверяй черновики, переключение режимов, задержанные ответы и ошибки;
  запускай существующие регрессионные проверки и дополняй их для нового поведения.
- После добавления Svelte запускай предусмотренные проектом проверку типов,
  lint, сборку и релевантные тесты; изменения Leaflet дополнительно проверяй в браузере.
- Изменения API, SQL, схемы и конфигурации БД проверяй интеграционно с настоящим
  изолированным PostGIS, миграциями и seed. Одних моков JdbcTemplate недостаточно
  для проверки геометрии, SRID, транзакций и ограничений БД.
- Изменения инфраструктуры проверяй с пустым demo-volume и повторным запуском;
  изменения публичного API — также на совместимость UI, документации и ошибок.
- Документационные изменения проверяй по фактическим файлам, путям и командам.
  Не добавляй тесты, которые лишь повторяют текст документа.
- Перед заявлением о готовности выполни подходящие проверки и прочитай результат.
  Различай проверку синтаксиса, тест с заглушками, интеграционный и браузерный тест.
  Если проверка не выполнена, укажи это и причину; не называй её успешной.
- Обновляй этот файл и README при изменении структуры, команд и обязательных проверок.
  Не выполняй публикацию или deployment без соответствующего разрешения пользователя.

## Git и pull request

Обычные задачи выполняй от актуального `stage` и после решения issue создавай PR
в `stage`. Используй `features/F-<номер>-<описание>`, `bugfixes/B-<номер>-<описание>`,
`chores/<номер>-<описание>` или `security/<номер>-<описание>` по типу работы.
Перед PR влей актуальный `stage` обычным `git pull --no-rebase origin stage`,
затем выполни относящиеся к изменению проверки. Не пушь код напрямую в `main`
или `stage`, не используй force push и не переписывай опубликованную историю.

Один коммит — одно логическое изменение, название в формате Conventional Commits.
Не коммить рабочие спецификации, implementation plans и planning-артефакты;
храни их локально в игнорируемой `.superpowers/`. Итоговая документация задачи
входит в репозиторий.

В PR указывай связанные issues, результат изменения, фактические проверки,
риски, миграции и конфигурацию. Зависимые PR связывай явно. Не объединяй PR
без отдельного указания пользователя; по workflow перед merge нужны одобрение
неавтора и успешные обязательные проверки. После merge удаляй только более
неиспользуемую рабочую ветку.

Процесс согласован пользователем по [Git Workflow](https://repo.dvgups.ru/docs/Разработка/Git-Workflow)
и [Git Agent Rules](https://repo.dvgups.ru/docs/Разработка/Git-Agent-Rules).
